### 0.3 三个关键取舍

1. **版本哈希用「只含审核范围文件的 git 树哈希」**。它按内容寻址，不看修改时间，可以直接拿来 `git diff` 和 `git commit-tree`;临时索引热跑只要 0.5 s。
2. **不从审核过的树单独构建，改成构建前后各算一次树哈希，两次都要等于审核单里的哈希**。原因是 pnpm workspace 的包链接指向工作区，另开目录构建反而可能混进工作区的代码。前后校验再加上线锁，留下的空档只有几秒。
3. **Laya 在校准前只能判「存疑」;Jev 可以判「机审拦」,但要两份报告才能推翻**。v1 实测 Laya 判拦时置信只有 0.20–0.40;Jev 官方的用法也是「置信度只决定要不要人看」。两家的约束力体现在：只要有一家存疑，这次上线就必须有 Claude 审核员逐条书面回应；Jev 高置信判拦时，还要再加一名反驳员才能推翻。Laya 要等红队集校准、精确率达到 0.8 以上，才开放「机审拦」。

另外，claude-guard 插件的命令分类器不直接拿来用：它把 `xargs`、`sed`、`tee` 引号里的参数当成普通数据清空，于是 `echo x | xargs "npx wrangler deploy"` 这一类写法就能绕过去。所以 hook 自己写，只借它「按分隔符切段、识别执行桥」的思路(§6.1)。

## 一、第一关·机器初审(gate1)

### 1.1 怎么跑，多快

- 入口：`python audit_v2/gate1.py --repo <仓库> [--worker <名>] [--mode build|ship|ops|prepush] [--files …]`。
  - 结果写到 `cache/gate1-<缓存键>.json`,同时打印中文摘要。
  - 退出码:0 = 过;1 = 拦;2 = 闸门自身出错，按拦处理。
- 步骤(括号里是耗时目标):
  1. 算树 T(约 0.5 s,算法见 §2.1)。缓存键 = sha256(T + 基准树 + 规则文件哈希 + 闸门哈希)。命中缓存就直接用结果(<1 s)。
  2. 用 `git diff --numstat` 和 `git diff -U0 <基准树> T -- <范围>` 取改动文件和新增行(约 0.3 s)。
  3. semgrep 只扫改动文件，只调一次(5–8 s):
     `semgrep scan --config tools-review/rules.yml --config audit_v2/rules-v2.yml --metrics=off --json -q -j 2 <改动文件…>`
     进程用 BELOW_NORMAL 优先级启动(CPU 高温规矩)。
  4. 用 blob 缓存判断哪些违例是「新增」(§1.3)。不再用 `--baseline-commit`:v1 慢就慢在它，外加第二遍全量扫。
  5. 跑差异规则、目录巡检，生成机器风险清单。这一步是 Python,不到 1 s。
  6. gitleaks:在 PATH 或 `_venv/review/bin` 里能找到，就对改动文件跑 `gitleaks dir --redact --no-banner`;找不到就跳过，由 semgrep 的 S1 规则兜底。下载安装 gitleaks 需要创始人同意。
- 耗时目标：热跑中位数 ≤10 s。冷跑(一次改了上百个文件)允许 20–30 s,这时打印各段耗时。**不会因为超时判拦。**

### 1.2 挂到构建上

两站的 `apps/web/astro.config.mjs` 各加一个集成。`astro:build:start` 在任何 `astro build` 之前都会触发:`npm run build`、`pnpm build`、平台 deploy.sh 里的 `npx astro build --outDir` 都覆盖得到。

```js
import { spawnSync } from 'node:child_process';
import { appendFileSync } from 'node:fs';
import { fileURLToPath } from 'node:url';
const PY = 'F:/0cosmetic/_venv/review/Scripts/python.exe';
const G1 = 'F:/0cosmetic/tools-review/audit_v2/gate1.py';
const gate1 = {
  name: 'bohui-gate1',
  hooks: {
    'astro:build:start': () => {
      const repo = fileURLToPath(new URL('../..', import.meta.url));
      const r = spawnSync(PY, [G1, '--repo', repo, '--mode', 'build'], { stdio: 'inherit' });
      if (r.status === 0) return;
      const bg = process.env.BOHUI_BREAKGLASS || '';
      if (bg.length >= 10) {   // 破窗：照跑，失败只警告，并记一行(Python 坏了也记得上)
        appendFileSync('F:/0cosmetic/tools-review/audit_v2/ledger/breakglass.jsonl',
          JSON.stringify({ ts: new Date().toISOString(), layer: 'astro', repo, gate1_exit: r.status, reason: bg }) + '\n');
        console.warn('[第一关] 破窗放行，已记账，24 小时内追审'); return;
      }
      throw new Error(`第一关未过(exit ${r.status ?? r.error}),构建中止`);
    },
    'astro:build:done': () => { /* §2.8 第③处：给产物 wrangler.json 注入 build.command */ },
  },
};
// export default defineConfig({ …, integrations: [gate1] })
```

- **失败即关**:找不到 python 或 gate1.py 时 `status` 为 null,同样中止构建。不提供任何「跳过」开关，唯一例外是破窗(§3.2)。
- ship.sh 的第 2 步也调 gate1(`--mode ship --worker <名>`)。两次调用的缓存键相同，所以构建时那一次 <1 s。
- 构建时不知道要上哪个 Worker,就用 `sites.json` 里该仓库标了 `primary` 的那个 Worker 的基准：公司仓是 bohui-web,平台仓是 beauty2ai。

### 1.3 「新增违例」怎么判(取代 `--baseline-commit`)

- 违例指纹 = `规则 id | 路径 | sha1(命中行去掉首尾空白)`,按多重集比较：同一文件里同一行文本出现两次，算两个。
- **基准一侧**的违例从 `cache/sg-blobs.json` 取，键为 `规则哈希:路径:blob id`,值是指纹列表。缓存里没有的：
  - 用 `git cat-file -p` 把这些文件在基准树里的 blob 写到 `cache/gate_base/<基准树前12位>/<原相对路径>`;
  - 在这个目录下用相对路径再扫一次。规则一样，路径锚点也一样；
  - 结果写回缓存。
- **当前一侧**:扫完就按 `规则哈希:路径:当前 blob` 写进缓存，下次它就成了基准。
- **新增 = 当前指纹 − 基准指纹。** 这样判的好处：
  - 只是行号挪了，不算新增；
  - 删掉 LIMIT,让原来那行变成违例，算新增；
  - 加了 `searchParams.get('q')`,让整文件规则命中老代码，也算新增。

  后两种情况，v1 那种只看新增行的判法会漏掉。
- 规则文件一改，规则哈希就变，缓存自然作废。

### 1.5 误报处理

1. **行内豁免**:semgrep 规则写 `// nosemgrep: <规则id> 理由`,差异规则写 `// gate-ok: <规则id> 理由`,放在命中行的行尾或上一行。缺规则 id 或理由 → K6 拦。每条豁免都记进审核单的 `exceptions[]`,合规、安全审核员必须看。
2. **路径例外**只能写在 `rules-v2.yml` 或 `sites.json` 里。改这两个文件算改闸门，要闸门审核单(§6.3)。
3. **历史违例**靠 blob 缓存自然放过，不需要 baseline 提交。
4. **误报率**:审核单记下每一条命中后审核员的结论(成立 / 误报)。某条规则两周内误报超过 30%,就开整改单改这条规则。
5. 存疑不拦构建，只要求审核员回应。所以拿不准的规则宁可定成存疑，也不要为了少报把规则写窄。

### 2.1 版本哈希

- **算法**:取「只含审核范围文件的 git 树对象 id」(SHA-1,40 位)。内容相同，哈希就相同；改一个字，哈希就变。
- **审核范围**(写在 `sites.json` 的 `scope` 里):

| Worker | 范围 |
|---|---|
| bohui-web | `apps/web`、`packages`、`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`tools/ship.sh` |
| beauty2ai | `apps/web`、`packages`、`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`tools/platform/ship.sh`、`tools/platform/deploy.sh`、`tools/platform/mkconfig.py` |
| 其他 Worker | 各自的目录，加上它的部署脚本(§8.1 第 1 项) |

- **怎样排除构建产物**:
  - .gitignore 已经排除的自动不进哈希：node_modules、dist/、.astro、.wrangler、.env*、*.log、data/ 等；
  - 再用 pathspec 排除 `**/dist*/**`(平台的 dist2、dist_HHMMSS 这些目录不在 .gitignore 里)、`**/*.bak*`、`**/nul`;
  - public/ 下的 .bak 会被发布出去，由目录巡检 S3 另查。
- **命令序列**(ticket.py 里用 subprocess 实现):

```bash
IDX=audit_v2/cache/tmp/idx.<pid>
cp "$(git rev-parse --git-dir)/index" "$IDX"      # 借用现有 index 的 stat 缓存，热跑 0.5 s
GIT_INDEX_FILE=$IDX git rm -r -q -f --cached --ignore-unmatch -- . ':!apps/web' ':!packages' ':!package.json' ':!pnpm-lock.yaml' ':!pnpm-workspace.yaml' ':!tools/ship.sh'
                                                   # 先删掉范围外的条目，只动临时索引
GIT_INDEX_FILE=$IDX git add -A -- apps/web packages package.json pnpm-lock.yaml pnpm-workspace.yaml tools/ship.sh ':!**/dist*/**' ':!**/*.bak*' ':!**/nul'
T=$(GIT_INDEX_FILE=$IDX git write-tree); rm -f "$IDX"
```

  不碰真正的暂存区，只往 .git/objects 里写 blob。v1 已经是这么做的。
- **另外记两个辅助哈希**:
  - `scope_sha256`:把 `sites.json` 里这个 Worker 的 scope 和 exclude 规范化后求 sha256。改了范围，审核单就作废；
  - `gate_hash`:闸门代码的哈希，见 §6.3。
- **本次改动** = `git diff -M <基准树> <T>`。基准树 = `refs/ship/<worker>^{tree}`。首次上线还没有这个 ref,就用 `git rev-parse <first_base>^{tree}`,并加 `-- <范围>` 限定路径。`first_base` 是 v1 的 BASELINE:公司站 5b98667,平台站 852ac8d。

### 2.2 定级

满足哪一级的任何一条，就升到那一级；几条都满足时取最高的。

| 级 | 条件 | 审核员 |
|---|---|---|
| 急修 | 说明里带【急修】,且 ≤30 行、≤3 个文件、不含 L3 的触发文件 | Jev + Claude 快审 1 名；Laya 上线后补跑 |
| L1 小改 | ≤80 行，不碰敏感文件，第一关没有存疑 | Laya + Jev + Claude 综合审核员 1 名(低强度) |
| L2 中改 | 81–400 行；或碰到敏感文件；或第一关有存疑 | Laya + Jev + Claude 2 名(「成本+正确性」「安全+合规」各一名) |
| L3 大改 | 下列任何一条:>400 行；依赖或锁文件变了；wrangler 配置(绑定、路由、vars、crons)变了;middleware.ts、lib/db.ts、鉴权会话、迁移目录变了；新增了 pages/api/** 文件；部署或上线脚本变了；首次上线 | Laya + Jev + Claude 4 名(每个角度一名)+ 反驳员(每条「拦」或「高」风险配一名) |

- **敏感文件**的正则沿用 v1 的 SENS,再加上 `pnpm-lock\.yaml|migrations/|/api/|/bohui/|/hosonzuo/|canon\.ts|searchGate|turnstile|cost|price`。
- **行数** = numstat 里增删行数之和。二进制文件按 0 行算；但 public/ 下新增超过 1 MiB 的二进制，要写进风险清单。
- **三家都审**:每一级都有 Laya、Jev、Claude 审核员三家参与，急修的 Laya 在上线后补跑。L1 也要派 1 名 Claude(低强度，小 diff 花不了多少 token),这是按创始人「三家共同判」「每次部署前」的要求。
- **L3 大 diff 分片**:
  - 先按角度把文件分出去(§2.4)。某个角度分到的超过 1,500 行，就按目录切片，每片 ≤1,500 行，每个角度最多 4 片；
  - 再大的话，ship.sh 提示「请拆批上线」。也可以在说明里写【整批】加理由硬上，审核单会记下来；
  - 首次上线公司站约 3,300 行，按这个办法估算约 40 万 token,只有这一次。以后每次上线的改动都小。

### 2.5 合并成三态(`ticket.py issue`)

按下面的顺序逐条判，一旦命中就停:

1. 第一关有「拦」→ **拦**。审核员推翻不了，只能改代码，或者按 §1.5 写带理由的豁免。豁免本身也是一处新改动，要重跑。
2. 本级要求的报告缺了任何一份；或者报告的 tree 对不上、不符合 schema → **待审**。这不是结论:ship.sh 会打印还要补哪几份，然后退出 2。
3. 任何一名 Claude 审核员判「拦」的发现，只要没有被反驳员拿证据推翻 → **拦**。
4. 机审拦(Jev 置信 ≥0.8):需要一名审核员在 addressed 里判它「不成立」,**并且**一名反驳员把它推翻，否则 → **拦**。推翻了的，记为「推翻机审」,日报里单独列出。
5. 下面这些，每一条都要在某一份审核员报告的 addressed 里得到回应，回应是「不成立」,或者是「成立但可以接受」并写明缓解办法：机审的存疑、第一关的存疑、行内豁免。有一条没回应 → **存疑**。存疑不放行，会打印缺的是哪几条。
6. 任何一份审核员报告判「存疑」→ 再派一名同角度的复核员。复核员判「过」,并且回应了那几个存疑点，才继续；否则 → **存疑**。
7. 以上都过了 → **过**。

签单时，把所有风险(第一关的 RK 加上各审核员报告里的 risks)合并去重，整理成五类清单：费用、安全、合规、正确性、回归。某一类没有条目的，要写「已查：<本类检查项 id>,未发现」,不许空着。

### 2.7 有效期与失效条件

- **有效期**:常规 24 小时，急修 2 小时。
- **提前失效**。下面任何一条发生，审核单就作废，不用等到期:
  - 工作区的树 ≠ 单上的 tree;
  - `refs/ship/<worker>` 已经不是单上的 base,也就是中间有人上线或回退过；
  - gate_hash 不在已批准的清单里；
  - 审核范围改了；
  - 审核单或任何一份报告的 sha256,与台账或单内记录对不上；
  - 台账链断了。
- 规则文件改了**不算**失效：每次跑 ship.sh 都会重跑第一关(命中缓存时 <1 s),新规则自动生效。

### 2.8 部署时怎样校验(三处)

`ticket.py verify --worker <名> [--ticket <路径>] [--stage ship|deploysh|wrangler]` 做 9 步检查。任何一步不过，就退出 1 并打印原因:
1. 重算树 T_now,必须等于 ticket.tree;
2. 审核单的 content_sha256 自洽，并且与 tickets.jsonl 里这个 id 的记录一致；台账链完整；
3. verdict 是「过」,当前时间早于 expires_at;
4. base.commit 等于当前的 `refs/ship/<worker>`。首次上线时，要求这个 ref 不存在，且 base.first_ship 为 true;
5. 本级要求的报告都在；报告文件的 sha256 与单内记录一致；报告里的 tree 等于 T_now;
6. gate_hash 在 `state/gate_approved.json` 里;scope_sha256 与 sites.json 一致；
7. 第一关按当前规则对 T_now 的结果是「过」(读缓存);
8. 费用灯:`d1_budget.py --check-deploy --note <说明> --semgrep-new 0` 退出码为 0;
9. 这个 Worker 没有逾期未追审的急修或破窗(§3.3)。急修通道本身不查这一步。

**三处调用**:
- **① ship_lib.sh 的第 5 步**,也就是主流程。
- **② 平台 `skin2oem/tools/platform/deploy.sh` 顶部**。它防的是直接跑 deploy.sh,别家 AI 和创始人终端里的直接调用也一样挡住:

```bash
TR=F:/0cosmetic/tools-review/audit_v2
if [ ${#BOHUI_BREAKGLASS} -ge 10 ]; then          # 破窗：放行并记账(§3.2)
  printf '{"ts":"%s","layer":"deploy.sh","reason":"%s"}\n' "$(date -Iseconds)" "$BOHUI_BREAKGLASS" >> "$TR/ledger/breakglass.jsonl"
elif ! { [ -n "$BOHUI_SHIP_NONCE" ] && F:/0cosmetic/_venv/review/Scripts/python.exe "$TR/ticket.py" verify --worker beauty2ai --stage deploysh; }; then
  echo "拒绝:deploy.sh 只能由 ship.sh 调用，而且要有有效的审核单。线上出事见 tools-review/audit_v2/设计-v2.md §3"; exit 1
fi
```

  公司站没有单独的 deploy.sh(部署写在 ship.sh 的 deploy() 函数里),不需要这一处。
- **③ wrangler 的自定义构建步骤**。它防的是有人进产物目录直接 `wrangler deploy`,别家 AI 也算在内。
  - 构建结束后，往产物的 `dist*/server/wrangler.json` 里写入:
    `"build": {"command": "F:/0cosmetic/_venv/review/Scripts/python.exe F:/0cosmetic/tools-review/audit_v2/ticket.py verify --worker <名> --stage wrangler"}`
    平台的 mkconfig 由这个文件生成 wrangler.copy.json,会一起带过去。
  - `wrangler deploy` 和 `wrangler versions upload` 都会先跑这条命令，退出码不是 0 就中止。
  - `--stage wrangler` 还额外要求：环境变量 `BOHUI_SHIP_NONCE` 与 `state/ship_nonce.json` 里的一致。这个文件由 ship.sh 在部署前写，15 分钟内有效；deploy.sh 超时重试时会复用，所以不做「用一次就作废」。手动设环境变量也能通过这一步，但 ship.jsonl 里不会有记录，每小时的对账会把它抓出来。
  - **需要实测的两件事**:
    - Astro 适配器写 wrangler.json,和我们的 `astro:build:done`,谁先谁后？我们要在它写完之后再改。
    - wrangler 4.x 有没有跳过自定义构建的参数？有的话，把它加进 hook 的拦截词。
  - 实测不通的退路：公司站把注入挪到 `apps/web/package.json` 的 build 脚本末尾；平台站挪到 deploy.sh 里 mkconfig 之后。

### 2.9 主线怎么用：一条命令反复跑

```
bash tools/ship.sh --note "说明"             # 公司站；平台站用 bash tools/platform/ship.sh
  → 退出 2「待审」时，照它打印的那行跑工作流:
    Workflow({name:'review-ticket', args:{draft:'F:/0cosmetic/tools-review/audit_v2/drafts/bohui-web-3fa9c1d2e0b4.json',
              worker:'bohui-web', tree:'<40位>', tier:'L2', angles:['成本+正确性','安全+合规']}})
  → 再跑同一条 ship.sh:签单 → 构建 → 部署 → 存版 → 冒烟
bash tools/ship.sh --status                   # 看当前的树、审核单、还差什么
bash tools/ship.sh --dry-run --note "…"      # 只审不部署。审核单照签，24 小时内真上线时直接用
```

- **review-ticket.js**:
  - 照 audit-dept.js 的写法，用 `agent(prompt, {schema, label, effort})`、`parallel`、`phase`;
  - 参数从 args 里取，因为脚本读不了文件，也取不了当前时间；
  - 每个审核员自己用 Write 写报告文件，同时把同一份 JSON 作为结构化结果返回；
  - 最后一步核对：每份报告的 tree 都要和 args.tree 一致；
  - L1 和急修用 `effort: 'low'`。
- **链式复审**(只改了一点点，不用全量重审):
  - 以上一张单的 tree 为基准。上一张单要么是「过」,要么是「拦」但只差修几处。新树和它相差 ≤80 行时，只审这一段增量；
  - 新单的 `prev_ticket` 指向上一张，基准就是上一张的 tree。上一张单里的每一条「拦」,都要由新单的审核员标成「已修」;
  - verify 会沿着 prev_ticket 链一路核到 refs/ship。链长最多 3 张，超过了就对「refs/ship → 当前树」全量重审。
- 人看的 `助手交付/上线闸门日志.md` 照写，格式沿用 v1,再加上审核单 id 和结论。**对账不再用它。**

## 三、紧急通道

### 3.1 急修(快，但不绕过审核)

用法:`bash tools/ship.sh --urgent --note "【急修】现象 + 影响 + 改了什么"`

- **条件**:
  - 相对 refs/ship ≤30 行、≤3 个文件，不含 L3 的触发文件；
  - 同一个 Worker 24 小时内最多 2 次；
  - 不满足就拒绝，改走常规流程或破窗。
- **必须过的检查**:
  - 第一关，不打折扣；
  - 费用灯。红灯时，说明里还要带【降读】或【安全】。请 D2 线在 d1_budget.py 的 MARKS 里加上【急修】,加上之前按这条执行；
  - Jev:几秒出结果，只记录，存疑不挡；
  - 1 名 Claude 快审员(综合四个角度,effort low,3 分钟内)判「过」。
- Laya 在上线后后台补跑，结果写进单子，给追审用。
- 审核单:tier=急修，有效期 2 小时,`followup_due` = 上线时刻 + 24 小时。

### 3.2 破窗(闸门自己坏了、线上正在出事时的最后手段)

- **写法**:bash 里在命令前加 `BOHUI_BREAKGLASS="理由(至少 10 个字)"`;PowerShell 里先执行 `$env:BOHUI_BREAKGLASS='理由'`。
- **效果**:
  - hook 放行，并在 `ledger/breakglass.jsonl` 记一行：时间、会话 id、工具、目录、完整命令、理由；
  - ship_lib、gate1、astro 集成、deploy.sh 看到这个变量，能跑的检查照跑，失败只记录、不拦；
  - 部署照样记进 ship.jsonl,action=breakglass。
- **立刻**开一张红色整改单「破窗上线」,并用 Server酱 推送(§4.5)。
- 同一个 Worker 24 小时内第 2 次破窗，Issue 加「需创始人」标签。

### 3.3 事后追审(24 小时内)

- **追审** = 对当时上线的那棵树补一张常规级别的审核单：`python ticket.py followup --worker <名> --tree <T>`。它会打印要跑的工作流，流程和 §2.9 一样；基准是上一次常规上线的快照。
- watch.py 每小时查一次：过了 `followup_due` 还没补审 → 开红色 Issue 并推送。**补齐之前，这个 Worker 的常规上线会被 verify 第 9 步一律拦下。** 急修通道还能用，但同样要挂账追审。
- 补审结论是「拦」→ Issue 升级为「线上存在未审问题」,主线必须修复或者回退。

## 四、第三关·上线后巡查

### 4.1 部署后立即做的事

ship_lib.sh 部署成功后，马上:
1. 记下 Version ID(用 v1 的正则 `Version ID: *[0-9a-f-]{36}`),写 ship.jsonl(§5.2)和本地快照(§5.1)。
2. 跑 `smoke.py --worker <名> --mode deploy`:
   - 破缓存：每个 URL 加 `?kk=<时间戳>`。?cb= 不进缓存键，破不了缓存；
   - 加上审核单里的 `smoke_extra`;
   - 公司站再跑 `node tools/ship-gate.mjs`,平台站再跑 `bash tools/platform/smoke.sh`。
3. 判定:
   - 关键 URL(每站首页和后台守卫)有 2 条以上 5xx 或超时，30 秒后重试(直连和 7890 各一次)仍失败 → **自动回退**到部署前记下的线上版本(`ship.sh --rollback`,见 §5.3),开红单并推送；

## 五、存版与回退

### 5.1 本地快照

- **ref**:每个 Worker 一条 `refs/ship/<worker>`,取代 v1 的 `refs/ship/last`。两个仓先执行 `git config core.logAllRefUpdates always`,让 refs/ship/* 也有 reflog。
- **部署成功后**:

```bash
PREV=$(git rev-parse -q --verify refs/ship/<w>)                  # 首次上线时为空，用 first_base 当父提交
NEW=$(git commit-tree <T_shipped> -p ${PREV:-<first_base>} -F <说明文件>)
git update-ref -m "ship <w> <VersionID>" refs/ship/<w> $NEW $PREV   # 带上旧值，防止并发覆盖
```

- **提交说明**(UTF-8):

```
ship bohui-web <Version ID>
ticket: RT-20260924-1932-bohui-web-3fa9c1d2 sha256:…
tier: L2 · 判官:laya 存疑→已回应 · jev 过 · claude 2 份过
tree: <T_shipped>(审核的是 <T_reviewed>;两者只差 CACHE_V 一行时写明)
note: 首页加洞察卡【降读】
time: 2026-09-24T19:40:02+08:00
```

- 父提交是上一次上线的快照，所以 `git log refs/ship/<w>` 就是完整的上线历史。快照里只有审核范围内的文件。
- **公开仓只存本地**:refs/ship/* 不是分支，普通 push 不会带上它。第二批的 pre-push 钩子再明确拒绝推送 refs/ship/*。本线不 push。

### 5.2 上线台账 `ledger/ship.jsonl`

每次部署、回退、破窗，都追加一行:

```
{"ts","worker","action":"deploy|rollback|breakglass|urgent","version_id","prev_live_version",
 "tree_reviewed","tree_shipped","ticket","ticket_sha256","snapshot","smoke":"ok|fail|rolled_back","note","prev"}
```

- `prev_live_version`:部署前用 `wrangler deployments list` 取当前的线上版本。自动回退就回到它，所以首次上线也有回退目标。
- 这份台账是对账的**唯一依据**,取代 v1 的 md 日志。md 日志照样写，但只给人看。

### 5.3 一键回退

**线上回退**(秒级，不重新构建):
- `bash tools/ship.sh --rollback --reason "…"` → 回到 ship.jsonl 里上一条成功上线的版本。
- `bash tools/ship.sh --rollback=<VersionID> --reason "…"` → 回到指定版本。这个版本必须在 ship.jsonl 里出现过，要么审核过，要么是那次上线之前的线上版本。
- **实现**:先按账号设好环境：公司站 source .env 里的 CLOUDFLARE_*;平台站去掉 CLOUDFLARE_*、走 OAuth,cwd 设为 apps/web。然后执行 `npx wrangler rollback <VersionID> --name <w> --message "<理由>"`。非交互确认用什么参数，实施时以 `--help` 为准。
- 回退**不需要审核单**,因为目标版本当时审过。但要做四件事：记台账；把 `refs/ship/<w>` 指回目标版本的快照，这样下次审核的基准就是真正在线的代码；跑一次破缓存冒烟；开 Issue 留记录。
- **注意，回退只回代码**:D1 迁移、secret、绑定都不会跟着回。diff 里有迁移目录或 wrangler 绑定变化时，ship.sh 在部署前就会在风险清单里写明「回退不可逆的项」。

**本地代码**(可选):
- 想看上次上线的代码：`git worktree add ../_ship_view_<w> refs/ship/<w>`。
- 想把工作区恢复成上线版：`git restore --source=refs/ship/<w> -- <范围>`。这会覆盖未提交的改动，先另存一份。

### 5.4 只审增量

下一次审核的 diff 是「`refs/ship/<w>^{tree}` → 当前树」,只包含上次上线之后的改动。回退之后，基准自动变成回退到的那个版本。

### 6.1 项目级 hook

写在 `F:/0cosmetic/.claude/settings.json`(项目级;全局 settings 不动):

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit",
        "hooks": [
          { "type": "command",
            "command": "F:/0cosmetic/_venv/review/Scripts/python.exe F:/0cosmetic/tools-review/audit_v2/hook_guard.py",
            "timeout": 10 }
        ]
      }
    ]
  },
  "permissions": {
    "deny": [
      "Bash(npx wrangler deploy:*)", "Bash(wrangler deploy:*)",
      "Bash(npx wrangler versions deploy:*)", "Bash(npx wrangler rollback:*)",
      "Bash(bash tools/platform/deploy.sh:*)"
    ]
  }
}
```

`permissions.deny` 这一段是 hook 脚本崩溃时的兜底。bypass 模式下它还生效不生效，由红队用例 H13 实测；不生效就把这段删掉。

**hook_guard.py 的逻辑**:
1. 从 stdin 读 JSON:tool_name、tool_input、session_id、cwd。
2. **Edit / Write / MultiEdit / NotebookEdit**:下面几种直接拒，其他文件放行:
   - `file_path` 指向 `F:/0cosmetic/.claude/settings*.json`(含 settings.local.json);
   - `file_path` 指向 `audit_v2/hook_guard.py`、`audit_v2/state/guard_unlock.json`;
   - 任何 `settings*.json`(包括全局的)的新内容里出现 `disableAllHooks`。

   原因：这几个文件是关掉约束的钥匙。
3. **Bash / PowerShell**:
   - 取出 `command`;
   - 先规范化：去掉路径前缀，合并空白，`wrangler.cmd`、`wrangler.js` 一律当 wrangler;
   - 再按 `&&`、`||`、`;`、`|` 和换行切成若干段。
4. **放行规则**:
   - 带 `BOHUI_BREAKGLASS=`、理由至少 10 个字 → 放行，记 breakglass.jsonl,并返回提示「已记破窗，24 小时内追审」;
   - 某一段是 `bash …/ship.sh …` 或 `ship_ops.sh` → 这一段放行。ship.sh 内部的调用 hook 本来就看不到，也不用管；
   - 某一段的第一个词是只读搜索(`grep`、`rg`、`git log|show|diff|grep`、`Select-String`、`findstr`),而且整条命令里没有 `| bash|sh|pwsh|powershell|cmd|iex|Invoke-Expression` → 这一段放行。`echo` 和 `printf` 不放行，因为 `echo … | bash` 就能绕过去；
   - `git commit -m` 或 `-F` 放行，提交说明里提到 deploy 很常见；
   - 临时解锁：`state/guard_unlock.json` 存在且没过期时，第 2 条对 hook 和 settings 文件的保护暂停。这个文件只能由 `BOHUI_BREAKGLASS="…" python audit_v2/ops.py unlock-guard` 创建，有效期 30 分钟，创建时记台账并开单。
5. **拦截词**。剩下的段里只要命中一条就拒:
   - `\bwrangler\S*\s+(?:.*\s)?(?:deploy|publish|rollback)\b`,但带 `--dry-run` 的不拦；`\bwrangler\S*\s+versions\s+(?:deploy|upload)\b`;
   - `\bdeploy[\w.-]*\.(?:sh|py|ps1|bat|cmd|mjs|js)\b`:平台的 deploy.sh、deploy-copy.py、网关的 worker/deploy.py 等一切部署脚本；
   - `\b(?:npm|pnpm|yarn)\s+(?:run\s+)?deploy\b`;
   - 对 `.claude/settings` 或 `hook_guard.py` 的写操作：命令里出现这两个路径，同时有 `>`、`sed -i`、`Set-Content`、`Out-File`、`Copy-Item`、`Move-Item`、`Remove-Item`、`rm`、`mv`、`cp`、`tee` 之一，就拒；另外命令里出现 `disableAllHooks` 也拒；
   - `\bclaude\b.*--(?:setting-sources|settings)\b`:防止嵌套启动 claude 时把项目设置排除在外；
   - 计划任务的定义变更:`schtasks\s+/(?:create|change|delete)`(`/change /enable|/disable` 不算)、`(?:Register|Set|Unregister)-ScheduledTask`,除非同一条命令里调的是 `audit_v2/ops.py register`(§7.3)。启用、停用(`Enable-ScheduledTask`、`Disable-ScheduledTask`)放行，由巡查去对照应启清单。
6. **拒绝时输出**:

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny",
  "permissionDecisionReason":"上线只走 ship.sh(见 tools-review/audit_v2/设计-v2.md §2.9);线上出事走 --urgent 急修，或 BOHUI_BREAKGLASS 破窗(§3)"}}
```

   同时在 `ledger/hook.jsonl` 记一行：时间、会话、命令的前 300 个字、命中了哪一条。
7. **hook 自己出异常**:全程用 try/except 包住。出异常时，命令里只要含 `wrangler|deploy|settings|hook_guard|ScheduledTask|schtasks|disableAllHooks` 就拒(失败即关),否则放行，免得整个会话瘫掉。
8. **生效时机**:hook 在新会话启动时加载。当前会话要重开，或者在 /hooks 里确认一下。
9. **管得到谁**:主线、主线派的子代理、工作流里的代理。管不到别家 AI 和人，这部分靠 §2.8 的②③和每小时对账。

  - audit_v2 下所有 .py/.sh/.json/.yml/.txt,不含 tickets/、reports/、ledger/、cache/、state/、logs/、drafts/ 这几个运行时目录；
  - tools-review/rules.yml、laya_judge.py;
  - 两站的 ship.sh、平台的 deploy.sh;
  - .claude/settings.json、review-ticket.js。
- **已批准清单** `state/gate_approved.json`,格式为 `[{"gate_hash","ticket","at"}]`。
- **改闸门**:执行 `bash audit_v2/ship_ops.sh gate --note "…"`。
  - 要过第一关，红队全套(`redteam/run.sh`)必须全过；
  - 级别至少 L2,安全和正确性两名 Claude 审核员必审；
  - 通过后签一张 kind=gate 的审核单，追加进批准清单，并在 tools-review 的本地 git 里提交一版。tools-review 要新做 `git init`,不设远端。
- **闸门没批准时**:ship.sh 第 0 步拒绝一切上线(破窗除外),watch.py 每小时开红单。
- **hook 和 settings.json** 由 hook 自己挡住 Edit/Write。要改，只能走 `ops.py unlock-guard` 破窗解锁(留痕、开单),或者由创始人手动改。

### 6.4 残余风险

- 同一台机器、同一个 Windows 用户(Administrator)下,Claude 能读写所有本地文件。台账链、审核单哈希、nonce 都只能防手滑、留痕迹，挡不住蓄意伪造。真正的隔离只有 6.2 里的 E(单独账户)和 F(云端部署):E 代价太高,F 违反零付费，都不做。
- 兜底是事后对账：每小时去比 Cloudflare 上的真实部署记录。这是本机改不了的外部事实。任何没有进台账的部署，最迟 1 小时内会开红单。
- Claude 审核员的报告，理论上可以由主线手写冒充。对策是：报告必须带 tree 和 run_label;审核部每周抽 3 张单复核(v1 设计里的 C 线)。
- `wrangler deployments list` 只返回最近 10 次：如果 1 小时内部署超过 10 次，就会漏看。这几乎不会发生；第二批接上 Cloudflare 审计日志来兜住。
- 构建前后两次校验之间，如果文件被改了又改回来，校验发现不了。只有蓄意这么做才会发生，接受这个风险。

### 7.1 登记表 `tasks.json`

```json
{

   "enabled_expected": true, "enforce": "report",
   "xml_sha256": "Export-ScheduledTask 导出后去掉 <Date>、<Author>、<URI> 节点再求 sha256",

   "files_sha256": "按路径排序，把 路径\\0内容 串联起来求 sha256",
   "ticket": "RT-…", "owner": "主线", "note": "网关：停了桌面端全挂，所以只报不拦"
 }
}
```

- **首次登记**:`python audit_v2/ops.py register --all`。把现有的 41 个 Bohui* 和 Beauty2ai* 任务(6 个启用、35 个停用)按现状登记为基线。基线单为 kind=task,tier=基线,verdict=过(存量)。历史不追审。
- **files 怎么定**:自动推导入口脚本，以及它一层之内调用的脚本(`python x.py`、`node x.mjs`、`call x.bat`);推导不到的，登记时手动补上。

### 7.2 脚本改动怎么审

用 `bash audit_v2/ship_ops.sh task <任务名> --note "…"`。不挂在任务上的单个脚本，用 `ship_ops.sh script <路径>`。

- **版本哈希**用 files_sha256。**基准**用登记表上次批准时存的文件副本(`state/ops_snap/<任务名>/`,每次批准时拷一份，diff 就对着它做)。这些脚本大多在 git 仓里，但未提交的改动很多，用副本最稳。
- **流程和网站一样**:第一关(tools 范围的规则，如 C4、C5、C7、C10、S1、S2、R4)→ 定级 → Laya + Jev + Claude → 审核单(kind=task)→ 更新登记表里的 files_sha256 和 ticket。
- **按路径分配角度**:路径含 `prospect|outreach|mail|send|crm` 的脚本，要加合规角度(发信用本站域名、商务条款)。
- 计划任务本身不需要重新部署：审过之后，下一次定时运行跑的就是审过的版本。

### 7.3 新增和修改计划任务

- hook 会挡掉直接的 `schtasks /create|/change|/delete` 和 `Register-/Set-/Unregister-ScheduledTask`。要改就用 `python audit_v2/ops.py register <任务名> --xml <任务定义.xml> --files …`:它先按 7.2 审脚本，审过了才真正注册任务、写登记表。注册命令在 ops.py 进程里执行,hook 看不到，也不需要看到。
- 启用和停用不拦，因为 D1 看门狗的红灯暂停和恢复就靠它们。巡查时对照 `enabled_expected` 和 expected_tasks.json。

### 7.4 巡查与运行时拦截

- **第一批：只报不拦。** watch.py 每小时用 `Export-ScheduledTask` 导出全部 Bohui* 和 Beauty2ai* 任务，算出 xml 和 files 的哈希，和登记表对比：有未登记的任务、定义变了、脚本改了没审 → 开红单并推送；应该启用的没启用 → 黄。
- **第二批：运行时拦。** 所有任务改成由 `audit_v2/launch.cmd <任务名>` 启动，它再调原来 run-hidden.vbs 的那条命令。启动前先核 files_sha256:
  - `enforce=block` 的，对不上就不跑，并开单；
  - `enforce=report` 的，照跑，并开单。网关、D1 看门狗、审核部自己这几个关键任务用 report,因为它们停了危害更大。
